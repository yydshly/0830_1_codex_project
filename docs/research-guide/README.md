# 研究方法

本仓库使用一条简单的证据链组织工作：

**问题 → 假设 → 基线 → 实验 → 证据 → 结论 → 新问题**

它不是对具体科研方法的替代，而是一套让软件与技术研究更容易复现、审查和展示的最小约定。

## 1. 定义可回答的问题

好的问题包含对象、版本、条件和判断标准。例如，“在固定数据集与预算下，A 库相对当前基线是否降低 P95 延迟且不降低正确率”，比“研究 A 库的性能”更容易完成。

开始前写明：

- 为什么值得研究；
- 本轮包括与不包括什么；
- 哪些证据会支持或推翻假设；
- 何时可以停止。

## 2. 固定研究对象

对外部库、仓库、模型或数据集至少记录一种不可变标识：

- Git commit SHA；
- 发布 tag 与解析后的精确版本；
- 包管理器锁文件；
- 数据集版本与校验值；
- 镜像 digest。

研究第三方代码前检查许可证。链接不等于授权，公开仓库也不等于可以任意复制和再分发。

## 3. 建立基线与对照

先验证当前方案或最小样例，再引入变量。一次实验尽量只改变一个关键因素；无法做到时，明确混杂变量。

性能结论至少记录硬件、操作系统、运行时、预热方式、样本数和统计口径。功能结论优先固化成自动化测试。

## 4. 记录实验

在 research-log.md 中保留原始观察与判断。建议每次实验包含：

1. 目标与对应假设；
2. 环境与锁定版本；
3. 相比基线的变更；
4. 可复现命令；
5. 原始观察和证据位置；
6. 判断与下一步。

不要用重写历史的方式掩盖失败。过时结果可以标记为被后续实验取代，但应保留原因。

## 5. 管理证据

证据优先级通常为：

1. 可自动运行的测试与基准；
2. 结构化数据和生成脚本；
3. 完整日志与环境信息；
4. 截图或录屏；
5. 主观描述。

只提交理解结论所必需的小型产物。大型数据、模型和二进制文件应存放在适合的平台，并记录稳定地址、版本和校验值。

## 6. 给出有边界的结论

结论必须说明：

- 哪项假设得到支持、被否定或证据不足；
- 适用版本与环境；
- 已知限制和未控制变量；
- 对采用、继续研究或停止研究的建议。

“在本次条件下未观察到”通常比“绝对不存在”更准确。

## 7. 发布与归档

进入已验证状态前，确保陌生人只依赖项目 README 就能理解并运行核心实验。归档项目时保留锁定版本、最终结论、复现方式，并解释停止原因。

## 外部仓库的接入方式

| 方式 | 适用场景 | 注意事项 |
| --- | --- | --- |
| 包依赖 | 只使用公开 API | 提交锁文件，记录精确版本 |
| 链接与脚本拉取 | 数据集或只读源码分析 | 记录提交和校验值 |
| Git submodule | 需要源码树或同步上游历史 | 固定 commit，说明初始化命令 |
| Fork | 需要持续修改并贡献回上游 | 明确与上游的差异和同步策略 |

不要把多个完整上游仓库直接复制进来。选择方式时同时考虑复现、许可证、仓库体积和后续更新成本。
